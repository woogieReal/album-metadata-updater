# CLAUDE.md와 커스텀 커맨드로 AI 에이전트에게 PDCA 개발 프로세스 주입하기

## 만든 계기

- 개발을 진행할 때 거의 동일한 패턴의 작업을 진행함
  1. 작업계획 수립
  2. 작업진행
  3. 테스트
  4. 작업내역 작성
- 물론 작업은 AI 에이전트가 하지만 매번 동일한 지시를 하는 것이 번거로웠음
- 하지만 규격화된 프로세스 없이 지시하면 매번 다른 포맷의 산출물을 만들어 내거나 테스트 단계를 건너뛰는 등의 문제가 발생
  - 산출물을 바탕으로 올바른 개발이 이루어졌는지 확인하는 입장에서 동일한 포맷의 문서 형식이 내용을 파악하기 효과적임
- 목표: PDCA 사이클(계획 → 실행 → 검증 → 보완 → 기록)을 AI 에이전트의 기본 행동 규약으로 만들기

## PDCA 워크플로우 설계

작업 흐름을 이렇게 정의했다.

```
[ /new-task ] ──> Plan (작업계획.md) ──> Do (코드 작업)
                                            │
                                            ▼
[ /work-log ] <── PASS ─── [ /check-task ] (검증결과.md)
(작업내역.md)                   │
                         NEED_ACT / FAIL
                                │
                                ▼
                         [ /act-task ] ──(수정/보완)──> [ /check-task ] (재검증)
```

각 단계는 명확한 산출물이 있다.

| 단계 | 커맨드 | 산출물 |
|------|--------|--------|
| Plan | `/new-task` | `작업계획.md` |
| Check | `/check-task` | `검증결과.md` |
| Act | `/act-task` | `작업중이슈.md` |
| Record | `/work-log` | `작업내역.md` |

단계를 건너뛰는 것을 막는 게 핵심이었다. 특히 Check 없이 Record로 바로 넘어가는 걸 방지하는 것.

## CLAUDE.md — AI의 행동 규약

Claude Code는 `~/.claude/CLAUDE.md` 파일을 대화 컨텍스트에 항상 주입한다. 여기에 워크플로우를 정의하면 AI가 모든 작업에서 이 규칙을 따르게 된다.

핵심은 **흐름도**와 **단계별 규격 표**를 함께 명시하는 것이다. 흐름도만 있으면 추상적이고, 표만 있으면 순서를 빠뜨린다. 둘을 같이 두니 AI가 "지금 어느 단계인지"를 스스로 인식하고 다음 단계를 제안하게 됐다.

```markdown
## 1. 작업 프로세스 흐름도

[ /new-task ] ──> Plan ──> Do ──> [ /check-task ] ──> ...

## 2. 단계별 규격 표

| Plan | /new-task | 작업계획.md | 목표, 세부 작업, 완료 기준 정의 | Do |
| Do   | 코드 구현  | 소스코드    | 계획 항목 구현. 완료 시 체크박스 업데이트 | Check |
...
```

## 커스텀 커맨드 구성

각 단계는 Claude Code의 커스텀 슬래시 커맨드(`~/.claude/commands/`)로 구현했다.

**`/new-task [작업명]`**
- `docs/` 폴더에서 기존 번호 패턴(`{n}_*`)을 찾아 다음 번호로 작업 폴더 자동 생성
- 작업 목표, 세부 작업 목록(체크박스), 변경 대상 파일, 완료 기준이 담긴 `작업계획.md` 생성

**`/check-task [경로]`**
- `작업계획.md`의 완료 기준과 실제 `git diff`를 비교
- 빌드·테스트 명령어를 직접 실행해 통과 여부 확인
- 결과를 `PASS / NEED_ACT / FAIL`로 판정하고 `검증결과.md` 작성

**`/act-task [경로]`**
- `검증결과.md`의 이슈 항목을 읽고 코드 보완
- 처리 내역을 `작업중이슈.md`에 기록
- 완료 후 `/check-task` 재실행

**`/work-log [경로]`**
- `작업계획.md`와 `git diff`를 읽어 작업내역을 자동 정리
- 무엇을, 왜, 어떻게 결정했는지를 `작업내역.md`로 남김

## 실제 사용 흐름

이 프로젝트(앨범 메타데이터 업데이터)에서 실제로 작동한 흐름은 이렇다.

```
/new-task UX 개선 — 탐색화면 시작 경로 및 메타화면 복귀 동작
  → docs/8_ux-improvement/작업계획.md 생성

AI가 코드 구현 (screens/explorer.py 수정)
  → 각 체크박스 완료 시 작업계획.md에 [X] 마킹

/check-task docs/8_ux-improvement
  → Textual Pilot 자동화 테스트 3건 실행
  → PASS → 검증결과.md 생성

/work-log docs/8_ux-improvement
  → 작업 목적, 결정 근거, 변경 파일 정리
  → 작업내역.md 생성
```

`/check-task`에서 실제 테스트를 실행하는 게 핵심이다. 코드가 "있는지"가 아니라 "동작하는지"를 검증하기 때문에, 이 단계를 통과하지 못하면 `/work-log`로 넘어가지 않는 규약이 의미를 갖는다.

## 삽질 기록

**Check 없이 Record로 건너뛴 사례**

실제로 AI가 `/check-task` 없이 바로 `/work-log`를 실행한 경우가 있었다. CLAUDE.md의 흐름도를 보면 명백히 잘못된 순서였는데, 지적하기 전까지 스스로 인지하지 못했다. 이후 흐름도와 규격 표를 더 명시적으로 수정했고, 재발은 없었다.

교훈: 규칙은 "적어두면 된다"가 아니라 "어길 수 없게 구체적으로" 써야 한다.

**체크박스 업데이트 누락**

Do 단계에서 코드만 짜고 `작업계획.md`의 체크박스를 업데이트하지 않는 경우가 반복됐다. CLAUDE.md의 Do 단계 설명에 "각 항목 완료 시 체크박스를 즉시 `[x]`로 업데이트한다"는 문장을 명시적으로 추가하고 나서야 지켜졌다.

교훈: AI에게 "당연한 것"은 없다. 원하는 행동은 전부 명문화해야 한다.

**커스텀 커맨드 프롬프트 품질이 결과를 결정**

`/check-task`가 "빌드와 테스트를 실행한다"고만 써두면 AI가 `import` 확인 정도로 때우기도 했다. "프로젝트의 빌드, Lint, 단위/통합 테스트 명령어를 **직접 실행**하여 통과 여부를 확인한다"로 바꾸고, 결과 템플릿에 실제 출력을 포함하도록 지시하자 제대로 된 검증이 이루어졌다.

## 마무리

- 산출물이 쌓인다: 기능 하나가 끝나면 `작업계획.md`, `검증결과.md`, `작업내역.md`가 자동으로 생긴다. 나중에 "왜 이렇게 만들었지?"를 추적하기 쉬워진다.
- AI가 스스로 단계를 챙긴다: "이제 /check-task 실행하겠습니다"처럼 다음 단계를 먼저 제안하는 경우도 생겼다.
- 규약의 정밀도가 전부다: 모호하게 쓴 부분은 반드시 AI가 임의로 해석했고, 문제가 생긴 후에야 명문화로 해결했다.
